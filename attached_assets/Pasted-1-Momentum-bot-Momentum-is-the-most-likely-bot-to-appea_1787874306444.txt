1. Momentum bot
Momentum is the most likely bot to appear inactive.
It still requires an open browser tab
Momentum’s scanning and auto-trading loop still lives in public/js/momentum.js.
It only trades when all of these are true:
* The Momentum page is open.
* The user has clicked the bot on.
* The browser still has botEnabled = true.
* The browser sees the Alpaca connection as active.
* The browser scan returned results.
* The market is between approximately 9:35 AM and 3:50 PM Eastern.
* The daily trade and loss limits have not been reached.
Closing the tab, logging out, refreshing into a new session, or losing browser state stops new Momentum entries and its strategy-specific monitoring.
Its scanner filters are very restrictive
The default Momentum profile requires:
* Price between $3 and $20.
* At least a 10% daily gain.
* Relative volume of at least 5x.
* A news catalyst.
* Float no greater than 10 million shares.
* At least 100,000 shares of volume.
* A minimum score of 4.
A stock must first pass those filters before it reaches the trade-safety checks.
Its final safety gate is even stricter
A candidate is rejected unless it has:
* A fresh game plan and technical data.
* Confirmed high confluence.
* Bullish score of at least 68.
* Bullish score greater than drawdown score.
* No elevated-risk condition.
* A valid structural invalidation level.
* Valid long-only price-action evidence.
* No strong dump indicators.
* No strong bearish candlestick pattern.
* Volume confirmation if it is close to resistance.
* A valid stop and take-profit configuration.
* Account equity available for sizing.
* Risk under the 5% per-trade cap.
* No existing position in the symbol.
* No active order or cooldown for that symbol.
This explains many legitimate no-trade cycles, but the site does not currently give the user a durable, server-side explanation for each rejected candidate.
Two additional Momentum problems are confirmed
* Only the top three qualifying candidates are passed to the final safety review. If those three fail, lower-ranked valid candidates are ignored.
* If the browser cannot load current positions, the code catches the error and continues with an empty holdings set. That can create duplicate-entry risk and should fail closed instead.
These are now tracked under Task #56 — Prevent Momentum from skipping valid setups or duplicating held positions.

2. Opening Momentum / PMH bot
PMH now has an always-on server scheduler, but it still requires:
* PMH settings enabled.
* The PMH bot toggle enabled.
* A dedicated PMH Alpaca connection.
* A valid active paper/live mode.
* The market to be open.
* A valid premarket snapshot.
* A valid previous-day high/close baseline.
* Opening price above the required baseline.
* A completed 2-minute candle breakout above the premarket high.
* Required volume and candle-quality confirmation.
* Fresh quotes and bars.
* Available position capacity.
* No unresolved entry intent or ambiguous broker order.
* A tradable Alpaca asset.
* Valid risk sizing and protected exit placement.
PMH also scans only the first 20 symbols in its fixed default list. A valid setup outside that list will never be evaluated.
The scheduler currently logs errors, but it does not consistently log successful scans, “no candidate” results, or the exact reason every candidate was rejected. That makes it difficult to tell whether PMH is inactive or simply has no qualifying setup.
The lack of a separate PMH live-arm confirmation is intentional under your policy: verified live connection plus bot enablement is sufficient.

3. UltraBot3 / Candlestick bot
Candlestick has a server-side scheduler, but it requires:
* Candlestick automation enabled in persisted settings.
* A dedicated Candlestick Alpaca account.
* The selected account mode to be valid.
* A live-arm confirmation when using live mode.
* The market to be open.
* A valid active/tradable Alpaca asset.
* A completed and fresh signal bar.
* A qualifying candlestick setup and score.
* Valid risk, position limits, and account capacity.
* No unresolved entry or protection state.
There is direct production evidence that Candlestick was being blocked:
Candlestick user ... cycle withheld: AAPL is not an active, tradable Alpaca stock or ETF.
That appeared repeatedly in the deployment logs. AAPL should normally be tradable, so this needs investigation into the account-specific asset lookup, catalog, credentials, or broker response. It is a concrete reason Candlestick did not place orders.

Cross-bot problems affecting trading
4. Bot controls do not represent all active bots
The shared bot toggle endpoint currently recognizes only countertrend and pmh.
Momentum and Candlestick have separate controls, so the central bot controls do not accurately describe or control all three active automation strategies.
The shared “trigger all bots” endpoint also acknowledges a scan but does not actually execute a bot cycle.
This makes the interface misleading when a user believes they started or triggered all bots.
This is tracked under Task #58 — Make bot controls and readiness status cover every active strategy.
5. The shared status page does not reflect actual bot readiness
The common bot-status route:
* Checks the manual Alpaca account rather than each bot’s dedicated account.
* Reads the legacy auto_trade_log.
* Does not represent the PMH or Candlestick journals accurately.
* Does not clearly show whether each scheduler is running.
* Does not identify which specific gate blocked a bot.
A user can therefore see a generally healthy account while the bot they expect to trade is disconnected, disabled, blocked by stale data, or using a different account.
6. Trading data is still local to one server instance
Important data remains in local SQLite, including:
* Broker connection records.
* Bot settings.
* Position and trade journals.
* Execution state.
* Bot enablement state.
The scheduler and bot locks are also in process memory.
This causes problems when:
* The app restarts.
* Requests reach different instances.
* The deployment scales horizontally.
* One process has newer state than another.
* A process dies during a broker order.
This is tracked under Task #49 — Keep trading settings and broker connections consistent when the site scales.
7. Broker timeout and partial-fill states are not fully resolved
An Alpaca order can be accepted even if the response times out. The site still needs to reliably recover:
* Filled entry with canceled remainder.
* Partial PMH lots.
* Replacement stops.
* Stop fills during discretionary exits.
* Manual closes.
* Failed cancellation requests.
* Broker positions that exist without a matching journal record.
Until this is hardened, a bot can appear not to have traded even though shares exist at Alpaca, or the journal can show an incorrect open/closed state.
Relevant work:
* Task #41 — Catch PMH broker timeout races before they can leave an entry unresolved
* Task #36 — Prevent PMH exits from misbehaving during broker order races
* Task #44 — Prevent one trading bot from canceling another bot’s stops or targets
* Task #45 — Keep trade records accurate after interrupted broker orders
8. One bot can still interfere with another bot’s position
Momentum, PMH, Candlestick, and manual trading may operate on the same Alpaca account.
The remaining risk is that one strategy can:
* See another strategy’s position as its own.
* Cancel another bot’s protective stop.
* Submit a generic close against a shared symbol.
* Attribute another strategy’s fill to its own journal.
* Produce incorrect strategy-level P&L.
This is especially dangerous when two bots trade the same ticker.
9. Momentum exits do not yet fully survive logout
Alpaca stop orders may remain at the broker, but Momentum’s configured strategy monitoring and reconciliation are browser-dependent.
After logout or tab closure:
* The browser-side take-profit monitor stops.
* Broker fill reconciliation can be delayed.
* Strategy-specific exits may not occur.
* The UI may not reflect the true broker position.
This is tracked under Task #33 — Keep automated position exits working after users log out.

Site-level problems that need attention
10. Broker credentials are stored directly in SQLite fields
The current schema contains api_key and api_secret columns, and the connection flow writes those values directly. I did not find an application-level encryption layer around them.
That is a production security concern, especially before moving the trading store to shared storage or backups.
This is tracked under Task #57 — Protect connected broker credentials before production scaling.
11. Catalog and data failures are not always visible
Several data-fetch paths return null or fall back to another source.
The site can therefore confuse:
* “No qualifying stock exists.”
* “The broker catalog failed.”
* “The market-data provider failed.”
* “The data is stale.”
* “The account is not authorized.”
* “The symbol is not tradable.”
The order validation is safer than the UI behavior, but the user experience still makes failures look like ordinary inactivity.
12. PMH candidate coverage is too narrow
PMH uses a fixed limited symbol list instead of broad rotating coverage from the verified Alpaca catalog.
This can make the bot look inactive simply because its small watchlist has no setup while another stock elsewhere in the market is breaking out.
13. Scheduler observability is insufficient
The current logs show startup and error messages, but not enough normal-cycle information.
The site needs a bot health view showing, per strategy:
* Last scheduler cycle.
* Last successful scan.
* Number of candidates evaluated.
* Top rejection reasons.
* Last broker request.
* Last reconciliation.
* Current account and mode.
* Current position/journal state.
* Whether the bot is disabled, disconnected, stale, rate-limited, or simply has no setup.
Without this, it is difficult to distinguish an intentional no-trade from a broken bot.
14. Deployment startup has avoidable warnings
The deployment logs show:
* Health checks failing briefly before the app finished starting.
* A PostgreSQL SSL compatibility warning.
* The app eventually starting successfully.
These did not appear to be the direct reason bots were not trading, but they should be cleaned up before relying on the deployment for unattended automation.
15. User-facing trading visibility is incomplete
The site still needs:
* News headlines in the stock detail panel.
* Catalyst scores directly in scanner rows.
* A live bot-session P&L curve.
* Historical rejected-setup review.
* Clear bot-specific readiness and no-trade explanations.
* Historical examples supporting forecasts.
* Clear recovery status when float or market data is missing.
* Automatic refresh of stale game plans after large price moves.
Existing work items cover most of these.
Bottom line
The most likely reasons a bot currently does not take a trade are:
1. Momentum requires the browser tab to remain open.
2. The strategy filters are extremely restrictive.
3. A candidate fails the final technical, risk, freshness, or price-action gate.
4. The bot’s dedicated account or enablement state is missing.
5. The broker catalog rejects the symbol; this has already appeared in Candlestick logs for AAPL.
6. PMH is scanning only a small fixed list.
7. A prior position, pending intent, daily limit, or unresolved broker order blocks a new entry.
8. The site does not clearly expose which of those conditions occurred.
The highest-priority fixes remain shared trading state, bot-specific readiness reporting, order ownership, broker-fill reconciliation, browser-independent exits, and the Momentum server-side scheduler.
