1. FIX MOMENTUM + PMH RECONCILIATION WHEN PAUSED

Current problem:

The Momentum and PMH schedulers only select users whose strategy settings are enabled.

Their cycle functions also return early when the strategy is disabled.

This means pausing a strategy can stop broker reconciliation and exit management.

Required architecture

Separate every strategy cycle into two distinct phases:

PHASE A — POSITION MANAGEMENT

This must run regardless of whether NEW ENTRIES are enabled.

Examples:

* fetch broker positions
* reconcile local positions
* synchronize broker orders
* update stop losses
* update take profits
* update trailing stops
* manage runners
* detect closed positions
* detect orphaned positions
* update lifecycle state
* process fills
* process exits

PHASE B — NEW ENTRY SCANNING

This phase must respect the user’s strategy-enabled setting.

Pseudo-architecture:

strategyCycle(user):
    runPositionManagement(user)
    if strategyIsPaused(user):
        return
    runEntryScanning(user)

NOT:

if strategyIsPaused(user):
    return

Also change scheduler queries so users with existing positions can still be selected for reconciliation even when the strategy is paused.

Ideally determine:

needsPositionManagement(user)
OR
strategyEnabled(user)

The scheduler should run a user if either:

1. They have active/open positions requiring management
2. The strategy is enabled and needs an entry scan

Do not require the strategy to be enabled merely to reconcile existing positions.

Apply this consistently to Momentum and PMH.

Add tests proving:

* enabled + no position → entry scanning works
* enabled + open position → management + entry scanning work
* paused + no position → no new entry scan
* paused + open position → position management STILL runs
* paused + open position → stops/targets/trailing logic STILL runs
* paused + broker position but missing local position → reconciliation STILL runs

3. REPLACE THE SHARED CROSS-BOT LOCK

Current problem:

Momentum, PMH, Candlestick, Swing, and Options all use one shared per-user lock.

A slow scan or broker request from one strategy can block another strategy.

This can cause missed short-lived entries.

The 90-second expiration also creates the possibility of overlapping cycles.

Required change

Replace the single shared bot lock with strategy-specific locks.

Example:

user:{userId}:lock:momentum
user:{userId}:lock:pmh
user:{userId}:lock:candlestick
user:{userId}:lock:swing
user:{userId}:lock:options

One strategy being busy must NOT prevent another strategy from running.

However, broker-level operations that genuinely must be serialized should remain protected separately.

Separate:

strategy execution lock

from:

broker/account critical-section lock

Do not simply remove locking.

Implement robust lock behavior with:

* unique lock ownership/token
* acquisition timestamp
* heartbeat/lease renewal if cycles can exceed the lease
* safe release only by the lock owner
* bounded timeout
* stale-lock recovery
* logging
* metrics

Do NOT rely on a fixed 90-second timeout if a legitimate cycle can exceed 90 seconds.

A lock must never expire while the original process is still actively executing unless ownership has been safely transferred.

Add tests proving:

* Momentum busy → PMH still runs
* PMH busy → Swing still runs
* Options busy → Momentum still runs
* same strategy cannot execute concurrently
* stale locks recover
* a long-running cycle does not accidentally overlap itself

6. FIX LEAP SIGNAL RESERVATIONS

Current problem:

A reservation is inserted for a symbol + completed weekly signal but is never deleted.

A canceled/rejected/no-fill entry can permanently consume that signal.

We need to distinguish:

Successfully consumed signal

From:

Failed/recoverable attempt

Implement explicit reservation lifecycle states.

For example:

RESERVED
ENTRY_SUBMITTED
FILLED
CANCELED
REJECTED
EXPIRED
RELEASED

A signal should remain permanently consumed only when the business logic determines that it has actually been consumed.

Recoverable failures should release the reservation.

Examples of potentially recoverable conditions:

* quote unavailable
* broker timeout
* temporary data failure
* order canceled without fill
* transient broker rejection
* insufficient liquidity at execution time

Non-recoverable/business-rule failures may remain consumed.

Do NOT simply delete every reservation after an error.

Implement an explicit state machine.

Also protect against duplicate concurrent reservations using an atomic database constraint/transaction.

Add tests for:

* reservation created
* successful fill permanently consumes signal
* canceled no-fill releases reservation
* recoverable rejection releases reservation
* transient broker failure releases/retries appropriately
* duplicate concurrent attempts cannot create duplicate entries
* already-consumed signal cannot be entered twice
