You are performing a SECURITY HARDENING AND SAFETY AUDIT of an existing production financial/trading application.

==================================================
PHASE 2 — USER DATA ISOLATION
==================================================

This is the highest priority.

Guarantee strict server-side tenant isolation.

Every request involving user-owned data must verify ownership SERVER-SIDE.

Never trust:

- user_id supplied by frontend
- account_id supplied by frontend
- broker_connection_id supplied by frontend
- order_id supplied by frontend
- position_id supplied by frontend
- bot_id supplied by frontend
- watchlist_id supplied by frontend
- settings ID supplied by frontend

Example:

Authenticated User A must NEVER be able to access User B's:

- broker credentials
- brokerage account
- positions
- orders
- trading history
- bot settings
- watchlists
- alerts
- strategy configuration
- account settings
- activity logs
- performance data

Do not rely on frontend filtering.

Authorization must happen on the backend/database query.

Bad:

SELECT * FROM positions WHERE id = requested_id

Good:

SELECT * FROM positions
WHERE id = requested_id
AND user_id = authenticated_user_id

Apply this principle throughout the entire application.

Look specifically for:

IDOR
BOLA
Broken Access Control
Privilege Escalation
Horizontal Privilege Escalation
Vertical Privilege Escalation

PHASE 3 — ALPACA CREDENTIAL SECURITY
==================================================

Treat broker credentials as HIGHLY SENSITIVE.

Never expose Alpaca API secrets to the browser.

Never return them through API responses.

Never store them in:

- localStorage
- sessionStorage
- frontend state unnecessarily
- URLs
- query parameters
- cookies
- client-side configuration
- analytics
- error messages

Never send broker secrets to:

- AI models
- analytics systems
- third-party APIs
- frontend logging
- telemetry

Search the entire repository for:

ALPACA
API_KEY
API_SECRET
SECRET
PASSWORD
TOKEN
AUTHORIZATION

Determine where credentials are stored.

If credentials are stored in the database:

- encrypt them at rest using authenticated encryption
- keep encryption keys outside the database
- use environment-managed secrets
- never log plaintext credentials
- decrypt only on the server when actually required
- minimize credential exposure
- securely delete/revoke credentials when disconnected

IMPORTANT:

Do not expose encryption keys in source code.

Do not commit secrets to Git.

Do not print secrets during debugging.

PHASE 4 — LIVE VS PAPER TRADING
==================================================

This is CRITICAL.

Never trust the frontend to determine whether an account is:

PAPER
or
LIVE.

The backend must determine the actual environment.

A malicious user must not be able to modify a frontend request such as:

{
  "mode": "paper"
}

into:

{
  "mode": "live"
}

and bypass safeguards.

Every broker request must verify:

1. authenticated user
2. authorized broker connection
3. correct owner
4. correct broker account
5. correct environment
6. requested operation
7. current user permissions

==================================================

Strengthen authentication without breaking existing users unnecessarily.
