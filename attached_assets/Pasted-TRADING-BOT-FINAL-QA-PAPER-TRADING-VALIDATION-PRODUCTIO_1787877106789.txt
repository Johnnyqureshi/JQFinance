3. INTERRUPTED BROKER ORDER RECOVERY

Implement and test robust recovery for:

* Momentum
* PMH
* Candlestick

The system must survive:

Scenario A

Order submitted → broker response lost → process continues.

Scenario B

Order submitted → broker response lost → process restarts.

Scenario C

Order submitted → partial fill → process restarts.

Scenario D

Order submitted → complete fill → process restarts before local state updates.

Scenario E

Exit submitted → broker response lost → process restarts.

Scenario F

Cancel submitted → broker response lost → process restarts.

After restart, the system MUST query the broker and reconstruct the actual state.

Never assume:

“No response = no order.”

Instead:

1. Query broker orders.
2. Query broker positions.
3. Match orders using persistent client/order IDs.
4. Reconcile local state.
5. Restore protection.
6. Resume management.

⸻

4. IDEMPOTENCY / DUPLICATE-ORDER PROTECTION

A major requirement is preventing duplicate entries.

Before submitting a new entry, check:

* Existing local position
* Existing broker position
* Existing open entry order
* Existing pending order
* Existing strategy position
* Recently submitted client order
* Reconciliation state

If the symbol is already held by the same strategy, DO NOT submit another entry unless the strategy explicitly permits scaling.

If an order submission may have succeeded but the response was lost, DO NOT blindly submit another order.

First reconcile with the broker.

Use persistent unique client/order identifiers wherever supported.

⸻

5. CROSS-BOT ISOLATION

Momentum, PMH, and Candlestick must be completely isolated.

One strategy must NEVER accidentally:

* Cancel another strategy’s order
* Modify another strategy’s stop
* Exit another strategy’s position
* Reconcile another strategy’s order as its own
* Treat another strategy’s position as its own
* Duplicate another strategy’s entry
* Overwrite another strategy’s journal record

Build explicit strategy ownership into order/position state.

Every managed order should have identifiable metadata such as:

* strategy
* symbol
* bot/session
* position identifier
* client order ID
* lifecycle state

When reconciling, only modify orders that belong to that strategy.

Also test hostile/unusual broker responses where:

* Orders are returned out of order
* Multiple strategies trade the same symbol
* An order appears without local state
* A local order disappears temporarily
* Broker returns duplicate records
* Broker returns delayed status information

11. RECONCILIATION ENGINE

Build/verify a reliable reconciliation process.

At startup and periodically afterward:

1. Retrieve broker positions.
2. Retrieve broker open orders.
3. Retrieve relevant recent orders.
4. Compare against local database/state.
5. Identify discrepancies.
6. Resolve safe discrepancies automatically.
7. Flag ambiguous discrepancies for user review.
8. Never create duplicate orders during reconciliation.

Important:

Broker state is authoritative for actual positions and orders.

Local state should track and explain that broker state, not blindly override it.
